> 日期：2026-08-14

## 一、作品详情页延迟诊断

### 1.1 用户反馈

从首页点击作品进入详情页，体感约 0.5 秒的明显延迟。

### 1.2 实测数据（Playwright 模拟真实点击 + curl 分层计时）

| 环节                                  | 冷态（首次访问） | 热态（缓存命中） |
| ------------------------------------- | ---------------- | ---------------- |
| 首页 SSR TTFB                         | 122 ms           | 17 ms            |
| 作品详情 API `/api/v1/works/[id]`     | 57 ms            | 22 ms            |
| 评论 API `/works/[id]/comments`       | **531 ms**       | 13 ms            |
| 相关作品 API `/works/[id]/related`    | 31 ms            | —                |
| 评分 API `/works/[id]/ratings`        | 136 ms           | —                |
| 点击卡片 → 详情内容可见（Playwright） | —                | **107 ms**       |

### 1.3 根因：三个因素叠加

1. **dev 模式按需编译（最大头，仅 dev 存在）**
   Next.js dev 下每个路由/API 首次命中都要现场编译。评论 API 首次 531ms vs 热态 13ms，差值 500ms+ 正好对应体感的「半秒」。**生产 build 后此项完全消失**。

2. **作品卡片无路由预取**
   `WorkCard` / `FineCard` 用的是 `<div onClick={() => router.push(...)}>`，而不是 `<Link>`。
   后果：Next.js 无法在卡片进入视口/悬停时预取路由数据，点击瞬间才从零开始请求。

3. **详情页纯客户端渲染，存在请求瀑布**
   `src/app/(site)/work/[id]/page.tsx` 整页 `'use client'`：
   导航 → 拉 RSC payload → 渲染「加载中…」→ 浏览器发起作品 API → 再渲染内容。
   用户看到的是串行链条，且中间有「加载中…」闪一下。

### 1.4 修复方案（三项全做）

| #   | 修复                                                                                                                                 | 收益                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| F1  | `WorkCard` / `FineCard` 外层改 `<Link href="/work/[id]">`（内部作者跳转保留 stopPropagation）                                        | 卡片进入视口即预取路由 payload，点击后近乎瞬时切换                        |
| F2  | 详情页拆为 **server component 直连 `workService.get(id, viewerId)`** + 客户端子组件接收 `initialWork`（`useQuery` 的 `initialData`） | 「加载中…」闪烁消失，RSC 到达即有完整内容；评论/相关/评分仍客户端并行拉取 |
| F3  | `useWork` hook 支持 `initialData` 注入                                                                                               | 配合 F2，缓存无缝衔接后台刷新                                             |

预期：热态点击 → 内容可见 < 50ms（预取命中时接近 0）；dev 冷态首次访问仍有一次编译开销，属正常。

## 二、首页专区导航重构

### 2.1 现状问题

首页是**单一滚动长页**：「今日免费推荐」→「精品专区」→「排行榜」依次堆叠。
免费内容（校园互助属性）与付费精品（自我提升属性）混在一屏里，用户无法按意图分流，付费区也缺乏「值得付费」的仪式感。

### 2.2 设计目标

- 免费与付费内容**入口级分离**，而不是滚动顺序分离；
- 两个专区有明确的定位差异与视觉差异；
- 保留排行榜等社区元素。

### 2.3 信息架构

```
首页 /
├── 专区切换导航（sticky，两枚大入口）
│   ├── 🏫 校园专区 —— 免费 · 学长学姐的真诚分享
│   └── 🚀 自我提升区 —— 付费精品 · 为成长投资
│
├── [校园专区 视图]
│   ├── 关注动态（见第三节，登录且有关注时显示）
│   ├── 今日免费推荐（作品 grid）
│   └── 排行榜（助人/好评/收藏/创作者）
│
└── [自我提升区 视图]
    ├── 精品专区（更大篇幅的作品 grid，突出评分/帮助人数/价格）
    └── 付费价值说明（为什么值得付费）
```

### 2.4 交互设计

- **切换控件**：双卡式分段导航（非小 tab），两枚入口各占一半宽，带图标 + 主标题 + 一句定位文案；激活态高亮，sticky 在顶栏下方，滚动时始终可达。
- **状态保持**：切区为纯前端状态切换（无整页刷新），初始值读 URL `?zone=growth`，支持从顶栏直达。
- **全局导航**：顶栏新增「校园专区」「自我提升」两个链接，任何页面都能一键回区。

### 2.5 视觉规范（沿用现有 token）

- 校园专区：主色 `--pri-600`（红），强调「免费」徽章、互助文案；
- 自我提升区：金色系点缀（💎 徽章已有），入口卡加细边框与浅底；
- 激活态：加粗 + 底色 `--pri-50` + 下划线条。

## 三、关注动态信息流（社区属性强化）

### 3.1 现状问题

- 关注的创作者更新后，动态藏在顶栏一个小铃铛（「动态」）背后的 `/following` 独立页里，**首页完全看不到**；
- 首页没有任何「人」的元素（只有作品与榜单），不像社区，像商城。

### 3.2 设计

**位置：专区切换导航之下、作品列表之上——首页第一屏。**

```
┌──────────────────────────────────────────────┐
│ 🔔 关注动态                    查看全部 →     │
│ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │
│ │创作者A │ │创作者B │ │创作者C │ │创作者D │ │  ← 横向动态卡
│ │发布了..│ │更新了..│ │分享了..│ │发布了..│ │
│ └────────┘ └────────┘ └────────┘ └────────┘ │
└──────────────────────────────────────────────┘
```

- 登录且已关注：展示最近 4 条动态（复用 `DynamicCard`，横向 4 列），右上角「查看全部 →」进 `/following`；
- 登录但未关注：显示引导条「关注喜欢的创作者，TA 的新作品会第一时间出现在这里」+ 推荐入口；
- 未登录：显示登录引导条（不打扰，仅一条）；
- `useFollowingFeed` 增加 `enabled` 门控（仅登录时请求），消除匿名 401 噪音。

### 3.3 社区感强化点

| 手段         | 落点                               |
| ------------ | ---------------------------------- |
| 关注关系可见 | 首屏动态流，创作者头像+时间        |
| 互助氛围     | 排行榜保留在校园专区首屏下方       |
| 更新可追随   | 动态卡直接点进新作品，转化路径一步 |

## 六、运维备注：dev 偶发 500 / EPERM 的根因

排查过程中确认：**从 Claude Code 沙箱 shell 启动的 `pnpm dev`，其 node 子进程会被 macOS TCC 拒绝读取 Desktop 下的项目文件**（`EPERM: scandir src/app` / `uv_cwd` / webpack cache 写入失败），导致全站 500、导航栏消失（即上一轮修的 bug）。
**从用户自己的终端启动的 dev 一切正常**。若再遇到整站 500 + nav 消失，先确认 dev 进程是否由沙箱/异常父进程启动，在自己终端重启 `pnpm dev` 即可恢复。

**连带故障（2026-08-14 22:15 已修）**：EPERM 风暴过后 `.next` 里会残留损坏的编译产物，表现为 **CSS 404 → 整页无样式裸奔**（顶栏拉高、布局全乱）。修复：`rm -rf .next && pnpm dev`。排查命令：`curl -s localhost:3000 | grep -oE 'href="[^"]*\.css[^"]*"'` 拿到 CSS 地址后看状态码是否 200。
